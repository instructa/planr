## CLI Commands

```bash
planr evidence policy --json
planr evidence policy --check --json
planr evidence obligation add --input obligation.json --json
planr evidence obligation list --plan <plan-id> --json
planr evidence obligation show <obligation-id> --json
planr evidence capability list --json
planr evidence capability show <capability-instance-id> --json
planr evidence run --input run.json --json
planr evidence import --input import.json --artifact-root . --json
planr evidence host-capture import --input host-import.json --json
planr evidence host-capture run --input host-run.json --json
planr evidence attempts --obligation <obligation-id> --json
planr evidence receipts --obligation <obligation-id> --json
planr evidence coverage --scope obligation --id <obligation-id> --json
planr evidence coverage --scope criterion --id <criterion-id> --json
planr evidence coverage --scope item --id <item-id> --json
planr evidence coverage --scope plan --id <plan-id> --json
planr evidence explain --scope plan --id <plan-id> --json
planr evidence readiness --scope plan --id <plan-id> --json
planr evidence migrate --input migration.json --json
planr evidence migrate --input migration.json --apply --json
planr evidence rebind --input rebind.json --json
planr evidence rebind --input rebind.json --apply --json
planr evidence classifications --json
```

Exit code `0` means the command succeeded and the Evidence verdict is passing or informational. Exit code `2` is an unsatisfied Evidence verdict. Exit code `3` is blocked. Exit code `1` is request or execution error. The JSON envelope carries `schema`, `command`, `ok`, `object` or `error`, and `exit.code`.

## Run Input

Process-backed runs accept a JSON object like:

```json
{
  "obligation_id": "pob-public-run",
  "capability_instance_id": "capinst-verifier-generic-adapter-...",
  "target": { "kind": "process", "uri": "local://health" }
}
```

`manifest_id` can replace `capability_instance_id` when the command should probe the manifest and resolve an instance. `execution_contract`, `environment`, and `fixture_disclosure` are allowed only as untrusted inputs that Planr validates against policy and capability bindings.

These fields are rejected in public run input because only Planr can construct them:

- `attempt`
- `receipt`
- `receipt_json`
- `trusted_binding_json`
- `trusted_receipt`
- `receipt_status`
- `provenance`

## Migration

Migration turns pre-Evidence plan criteria into immutable `ProofObligation` rows.

```bash
planr evidence migrate --input migration.json --json
planr evidence migrate --input migration.json --apply --json
```

Preview is the default and does not write obligations. Apply is idempotent: duplicate IDs, lineage collisions, cross-project containment, and changed immutable fields are reported instead of silently rewriting history. Migration does not rewrite plans, logs, reviews, artifacts, or legacy claims.

## Readiness And Versioned Rebind

Run readiness before a binding goal starts. It checks that every active observation has a registered JSON Schema, a capability matching its observation type, payload schema, and runtime target, a current repository adapter digest, and an available runtime instance without executing the product oracle:

```bash
planr evidence readiness --scope plan --id <plan-id> --json
```

If a repository fixes an adapter contract after obligations were bound, create new obligation IDs that `supersede` the active IDs. Preview computes the immutable capability/obligation transition and returns `preview.preview_digest`. Copy that digest into the input before apply:

```json
{
  "schema_version": "planr.evidence.rebind.v1",
  "plan_id": "pln-example",
  "manifest_id": "verifier-project-v2",
  "obligations": [{ "id": "pob-new", "supersedes": "pob-old", "...": "full ProofObligation" }],
  "preview_digest": "sha256:..."
}
```

```bash
planr evidence rebind --input rebind.json --json
planr evidence rebind --input rebind.json --apply --json
```

Apply is one transaction. It refuses criterion, target, fixture, freshness, assurance, or expected-observation drift. Those are product-scope changes and require plan/user authorization, not a rebind.

Source freshness hashes product files plus repository-owned plans, policies, schemas, and adapters. Mutable Planr runtime outputs such as `planr.sqlite` and generated Evidence run, attempt, receipt, and coverage directories are excluded so recording a receipt cannot invalidate itself. Changing a policy, schema, adapter, or product file still changes the source binding.

## Real Configurable Examples

The executable examples live in [`apps/docs/scripts/generate-evidence-examples.mjs`](https://github.com/instructa/planr/blob/main/apps/docs/scripts/generate-evidence-examples.mjs) with the reusable policy/manifest builder in [`evidence-fixture-builder.mjs`](https://github.com/instructa/planr/blob/main/apps/docs/scripts/evidence-fixture-builder.mjs). They create fresh repositories and run the exact candidate binary.

### Command or backend observation

The queue-worker example registers `com.example.queue.depth.v2`, executes a repository-owned command, validates stdout against its registered payload schema, then evaluates coverage:

```bash
planr evidence readiness --scope criterion --id crit-pob-docs-queue-depth
planr evidence run --input pob-docs-queue-depth.run.json
planr evidence coverage --scope criterion --id crit-pob-docs-queue-depth
planr evidence explain --scope criterion --id crit-pob-docs-queue-depth
```

Its method is a process adapter because the required fact is backend queue state. It does not claim browser behavior.

### HTTP or API observation

The API example starts a real loopback HTTP service and configures a curl process adapter for `com.example.http.status`. Curl is sufficient here because the obligation requires only the HTTP response payload:

```json
{
  "type": "com.example.http.status",
  "subject": "health endpoint",
  "expected": { "status": "ok" },
  "payload_schema": { "schema_ref": "schema://com.example.http.status" }
}
```

The same curl capability is deliberately rejected by the separate `curl-http-not-browser` case when the obligation requires rendered browser facts.

### Rendered web observation

The full-stack example launches real Chrome and drives raw CDP. One structured execution returns six observations: rendered visibility, user interaction, navigation, network result, console errors, and persistence after reload. The outer execution contract uses `schema://planr.structured_observation_results.v1`; every inner `actual` value is separately validated against the JSON Schema registered for its observation type.

```bash
PLANR_BIN=target/debug/planr pnpm docs:evidence-examples:generate --live
```

CDP is only the configured method in this example. A native Browser host capture, Playwright, or another verified capability can satisfy the same obligations when it observes the same required facts and produces trusted provenance. A screenshot alone cannot prove reload persistence, and an HTTP response cannot prove rendered interaction.

## Host Capability Matrix

The generated host matrix is versioned at `tests/fixtures/evidence/host-capabilities/v1/expected/host-surface-matrix.json`. The docs example fixture records host matrix digest `sha256:dc4365247b11919b60b3bd4e922f60e63619eb1d58060d01655b6e05044a4df0`.

The matrix is intentionally honest:

- Available terminal or local-function probes do not automatically become trusted production adapters.
- Degraded browser surfaces are recorded as degraded, not silently upgraded.
- Unavailable app-server, exec stream, or MCP-server surfaces remain unavailable.
- A Chrome/browser-client capture can support browser proof only when Planr validates the required artifact, host identity, final CDP/DOM observation, target binding, and provenance.
- Playwright is not required for Evidence. It can be one possible host surface when available and validated.

## Waivers And Limits

Waivers are approval-backed exceptions for observations that cannot be proven by receipt. They should be scoped, reasoned, expiring, and auditable. A waiver can satisfy coverage for its declared observation; it cannot manufacture a receipt, hide stale evidence, or weaken namespace/schema/provenance rules.

Limits remain explicit:

- A valid import can persist artifact validation without creating trusted receipts.
- A trusted receipt can go stale after source, target, environment, policy, adapter schema, or configuration drift.
- A capability instance can expire or become invalid after environment or permission changes.
- A curl receipt can satisfy an HTTP obligation and still fail a browser-rendered obligation.
- Fixture-backed proof must disclose fixtures when policy requires it.

## Drift Gates

These commands fail when public surfaces or generated Evidence examples drift:

```bash
pnpm docs:evidence-examples:check
pnpm --filter @planr/docs reference:check
pnpm --filter @planr/docs verify:reference
```

The Evidence docs verifier reads `tests/fixtures/evidence/docs/v1/examples.generated.json`, `docs/contracts/fixtures/evidence/v1/schemas/evidence-contract-v1.schema.json`, and the host matrix fixture. It fails if case IDs, titles, proven scope, not-proven scope, schema digest, host matrix digest, or public reference links disappear from the docs.
