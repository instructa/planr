## Transport and protocol

Launch one newline-delimited JSON-RPC server in the workspace root:

```json
{ "command": "planr", "args": ["mcp"] }
```

An explicit database goes before `mcp`: `planr --db /absolute/project/.planr/planr.sqlite mcp`. `initialize` reports protocol `2025-03-26` with tools, resources, and prompts capabilities. Supported methods are `initialize`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/read`, `prompts/list`, and `prompts/get`. Notifications without `id` receive no response.

## Tools

Schemas are returned by `tools/list`. The [generated MCP schema inventory](/docs/reference/mcp-schemas-generated) is the sole exhaustive tool contract: it records every current tool and its complete input JSON Schema, including required and optional properties, types, descriptions, `additionalProperties`, defaults, and enums.

Tool families cover project inspection, maps and plans, items, routing and policy, leases and recovery, approvals, evaluations, Evidence and artifacts, and review and closure. Use those families to choose a workflow, then use the generated inventory for exact names and fields. This conceptual guide intentionally does not mirror the mutable runtime inventory.

Mutation preview behavior, booleans, required fields, defaults, and enums are schema-owned. Do not infer them from a family description.

## Resources

All resources return `application/json`:

- `planr://project/map`
- `planr://project/context`
- `planr://item/{id}`
- `planr://plan/{id}`
- `planr://log/{id}`

Unknown or missing IDs produce JSON-RPC errors. Resource templates use `{id}` substitution in the URI.

## Prompts

- `planr-plan` — prepare or refine planning work;
- `planr-work` — execute one map item;
- `planr-review` — audit a leased durable ReviewGate;
- `planr-map` — inspect and coordinate the graph;
- `planr-summary` — summarize evidence-backed completion.

## Install contract

`planr install <client> --dry-run` prints the complete client-owned MCP, role, skill, and hook-reconciliation paths for Codex, Claude Code, Cursor, Grok Build, and Pi without writing them. A non-dry install writes only repository-local files, with this ownership contract:

- Codex: the CLI writes `.planr/integrations/codex-mcp.toml` and `.codex/hooks.json`; the plugin owns all ten workflow skills; neither path writes Planr project roles or project skills.
- Claude Code: the CLI writes `.mcp.json`, standalone `.claude/agents/` roles, and `.claude/settings.json` hooks, but no project skills; the plugin owns all ten workflow skills and its plugin agents.
- Cursor: the CLI writes `.cursor/mcp.json`, both `.cursor/agents/` roles, all ten `.cursor/skills/` skill copies, and `.cursor/hooks.json`.
- Grok Build: the CLI document-preservingly reconciles only `mcp_servers.planr` in `.grok/config.toml`, writes both native `.grok/agents/` roles and the canonical `.grok/skills/` tree, and writes no hooks or project plugin. It is explicit opt-in and remains outside `--client all`.
- Pi: core Pi has no MCP surface. The CLI writes the canonical native Agent Skills under `.pi/skills/` and optional pi-subagents-compatible roles under `.pi/agents/`; it writes no settings, MCP, hooks, extension, or package state. Pi is explicit opt-in and remains outside `--client all`.

The Cursor dry-run additionally prints a `cursor://anysphere.cursor-deeplink/mcp/install` link whose embedded config (`planr mcp`, no `--db`) is safe at user scope because each workspace resolves its own database. Planr does not edit global client configuration without a separate explicit operator action; the deeplink requires the operator to click it and confirm inside Cursor.

`--no-mcp` skips only the project MCP artifact: Codex reconciles hooks only; Claude Code writes standalone roles and hooks but no project skills; Cursor writes roles, all ten skills, and hooks; Grok writes its native roles and skills; Pi always writes only its native skills and optional roles. `--no-hooks` is the independent hook opt-out and can be combined with `--no-mcp`; for Grok and Pi it is an explicit no-op because neither v1 integration has a hook contract.

## Results and errors

Successful tools return MCP text content whose text is serialized Planr JSON. Tool execution failures return `isError: true` with a text JSON error object and keep the server alive. Protocol failures use JSON-RPC codes: `-32700` parse error, `-32601` method not found, `-32602` missing/invalid parameters, and `-32603` internal error.

For workflows, see [Generic MCP](/docs/integrations/generic-mcp) and [Daily Worker Loop](/docs/guides/daily-worker-loop).
